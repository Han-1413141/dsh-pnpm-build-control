# 同一 Git 地址的重复安装修复

## 问题

DSH 0.2.0-rc.2 的 `pluginManager.installBundle` 在 pnpm 成功退出后，比较安装前后 `package.json` 中的依赖地址。地址没有变化时，它只尝试从用户输入中查找包名。

用户输入的是 Git 地址，而远端已经有新提交时，pnpm 会更新包内容和锁文件；依赖地址仍然相同，DSH 因而无法确定更新了哪个包，返回 `ambiguous-install` 并恢复原来的 manifest 和锁文件。包名恰好与仓库名称相同也不会使这个判断自动成功。

## 0.1.4 的处理

插件加载后，为包含上述判断逻辑的原生安装方法增加兼容处理：

1. 从当前 profile 的 manifest 中查找唯一匹配的 Git 来源，使用实际依赖名称，不猜测仓库对应的包名。
2. 将明确的 `包名@Git地址` 传给 DSH，让其原有备用判断能够确定目标。
3. 在这一次调用中，将 pnpm 的安装参数还原为用户输入的 Git 地址。pnpm 11.7.0 对带包名的 Git 输入会复用旧的锁定提交；保留原始地址才能重新解析 Git 提交。
4. 继续使用原生的文件锁、请求取消、构建审批、插件校验、启用和回滚流程。

支持将 `github:owner/repo`、`https://github.com/owner/repo` 和相应的 `.git` HTTPS 地址识别为同一来源。分支、标签和提交部分必须相同；不同凭据或传输方式不会被合并。新依赖和存在多个匹配名称的情况交给原生流程处理。已固定到某个提交的地址仍然安装该提交。

兼容处理只修改当前运行进程中的服务实例，不写入 DSH 应用安装文件，不在共享实例上临时替换 pnpm 方法。插件停用时恢复原方法。原生安装代码不符合已知缺陷结构时，不附加此处理。

## 验证

在 Windows 的 DSH 0.2.0-rc.2、内置 pnpm 11.7.0 上，`npm run test:install` 使用独立临时 `DSH_HOME` 和本地 Git 仓库运行完整 DSH 后端：

- 未加载修复时，确认 pnpm 已下载新内容，但 DSH 返回 `ambiguous-install` 并恢复旧锁文件。
- 加载修复后，同一 Git 地址和同一包版本号的新提交安装成功，保留新锁文件和新内容，返回需要重启。
- 没有新提交时重复安装成功。
- 新提交不再声明 DSH bundle 时，原生校验拒绝安装并恢复之前的 manifest 和锁文件。
- 停用本插件后恢复原生方法；内置设置接口继续可用。

这项修复不要求关闭构建审批。更新后的代码仍需完整退出并重新启动 DSH 才会加载。
